# Phase 2B 설정과 사용

## 현재 상태

실제 OpenAI Responses API 연결 코드, 구조화된 분석, 한국어·영어·베트남어·일본어·중국어 간체 번역, DB 저장, 검수 UI를 구현했습니다. **이 환경에는 OpenAI 키가 없어 실제 AI 호출은 검증하지 못했습니다.** 테스트의 AI 응답은 합성 모의 응답입니다. Supabase 인증·DB·RLS는 로컬 실제 서비스로 검증했습니다.

## 운영 설정 순서

1. [Phase 2A 설정](phase-2a-setup.md)에 따라 Supabase와 최초 관리자/교회를 준비합니다.
2. SQL Editor에서 기존 Phase 2A 마이그레이션 적용 여부를 확인한 다음 `supabase/migrations/202610190002_phase2b.sql`을 한 번 적용합니다. 기존 테이블을 초기화하지 않습니다. 운영 데이터는 적용 전 백업하세요.
3. `.env.example`을 참고해 서버의 `.env.local` 또는 배포 플랫폼 비밀 환경변수에 `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, `OPENAI_MODEL`을 설정합니다. 운영 모드는 `APP_MODE=auto`입니다. Phase 2A 인증만 사용할 때와 달리 Phase 2B 작업 기록에는 서버 전용 service role 키가 필요합니다. 어떤 비밀키에도 `NEXT_PUBLIC_`을 붙이지 마세요. 키를 채팅·Git·브라우저에 넣지 마세요.
4. 모델 후보는 `gpt-4.1-mini`입니다. 설치된 공식 SDK의 모델 목록과 공식 OpenAI Cookbook의 GPT-4.1 설명은 확인했지만, 현재 계정의 사용 가능 여부와 실제 구조화된 응답은 미검증입니다. [공식 모델 안내](https://platform.openai.com/docs/models)와 [요금](https://openai.com/api/pricing/)을 확인하세요.
5. Supabase의 `public.ai_policy` 한 행에서 모델명·입출력 토큰 단가·비용 한도를 확인해 수정한 뒤에만 `enabled=true`로 변경합니다. 초기값은 비활성입니다. **입력 1 / 출력 5 USD(백만 토큰당)는 검증되지 않은 예시이며 실제 요금이라고 사용하면 안 됩니다.** 브라우저에서는 정책을 변경할 수 없습니다. 모델명은 환경변수와 일치해야 합니다.
6. 서버를 다시 시작하거나 배포합니다. OpenAI 목적지 `api.openai.com`과 해당 Supabase 프로젝트 호스트에 HTTPS 접속이 가능해야 합니다. 이 클라우드의 현재 설정에는 OpenAI 허용 도메인과 비밀키가 없습니다. 클라우드 비밀 변수 등록에서는 `OPENAI_` 접두사가 예약되어 있으므로 해당 이름의 프록시 비밀 등록을 그대로 사용할 수 없습니다. 실제 실행 서버의 안전한 환경변수 설정 또는 로컬 `.env.local`을 사용하세요.
7. 합성 원고로 분석 및 5개 언어를 실제 생성하고 검수한 뒤 교회 운영에 사용하세요. 원고는 OpenAI로 전송되므로 교회의 원고 처리 방침을 먼저 정하세요.

SQL 정책은 SQL Editor의 테이블 편집 또는 UPDATE로 설정합니다. 먼저 다음 조회로 현재 값을 확인합니다.

```sql
select model, enabled, input_usd_per_million, output_usd_per_million,
       max_job_usd, church_daily_usd, global_daily_usd, user_requests_per_hour
from public.ai_policy;
```

가격·한도 변경은 이미 시작된 작업의 예약 단가를 바꾸지 않습니다. 잘못된 설정을 발견하면 우선 `enabled=false`로 신규 생성을 중지하세요.

## 화면 사용 순서

운영 로그인 → 설교 저장 → 설교 상세의 AI 분석 → 언어를 선택하여 번역 → 검수 화면에서 원문과 번역 비교·수정 → 검수 요청 → 목회자 또는 관리자 최종 승인 순서입니다. 각 언어의 작업 상태와 사용량을 별도로 표시합니다. 생성 버튼은 예상 최대 비용을 안내합니다.

원문 근거는 문단 번호와 실제 인용문으로 표시합니다. AI 교육용 요약, AI 성경 배경 보충 설명, 원문 근거를 구분합니다. 용어 기준은 검수자가 수정할 수 있고, 변경하면 기존 번역을 다시 생성·검수해야 합니다. 원문·분석·번역 수정이나 재생성은 승인을 해제합니다. 이전 원문/분석 버전의 번역이 남으면 최종 승인을 차단합니다.

원고는 최대 20,000자·비어 있지 않은 200개 문단입니다. 한 줄을 한 문단으로 다룹니다. 한국어 전체 원고는 원문의 줄바꿈까지 보존하며, 쉬운 설명은 장면별 요약으로 분리합니다. 다른 언어 전체 번역도 문단별로 대응시켜 저장합니다.

키나 모델·정책 설정이 없으면 생성 버튼이 비활성화됩니다. Supabase가 없거나 `APP_MODE=demo`이면 기존 Demo Mode를 사용합니다. `/demo`는 운영 세션과 무관한 샘플입니다. 5개 언어는 운영 번역 화면에 추가했고 기존 3개 언어 데모는 유지했습니다. 승인된 운영 원고도 이번 단계에서 익명 공개하지 않습니다.

## 비용과 장애 처리

- DB 트랜잭션으로 사용자별 기본 6회/시간, 건당 0.50 USD, 교회별 5 USD/일, 전체 10 USD/일 상한을 검사합니다. 일자는 UTC 기준입니다.
- 입력 JSON·스키마·시스템 지시문 UTF-8 길이를 사용한 보수적 입력 토큰 추정과 출력 상한(기본 12,000 토큰)으로 최대 비용을 먼저 예약합니다. 입력 추정이 100,000을 넘으면 차단합니다.
- 응답의 실제 토큰 사용량을 기록해 설정 단가로 정산합니다. API 실패 등으로 사용량을 모르면 예약액을 유지합니다. 실제 계산 비용이 예약액을 넘으면 신규 생성을 비활성화합니다. 이 장부는 공급자의 청구서를 대신하지 않습니다.
- 동일 요청 키와 처리 중인 동일 설교·언어 작업은 중복 호출을 막습니다. SDK 자동 재시도는 끄고 사용자 재시도마다 새 작업으로 비용을 예약합니다.
- 원본과 결과 버전을 확인하여 실행 중 수정된 원고에 오래된 결과를 덮어쓰지 않습니다. 실패 사유는 안전한 코드와 한국어 안내로 남기고 원문은 유지합니다.
- API 시간제한 90초, DB 작업 만료 3분입니다. 화면에서 만료 작업을 정리하고 다시 시도할 수 있습니다. 별도 상시 백그라운드 워커는 없습니다. 배포 런타임이 서버 작업 최대 180초를 지원하는지 확인하세요. 프로세스 중단 시 작업이 자동 재실행되지는 않습니다.

## 로컬 검증

기존 합성 로컬 DB/Auth/PostgREST와 게이트웨이를 사용합니다. 새 환경은 Phase 2A 테스트 안내대로 준비하세요. 기존 `.env.local`이나 컨테이너를 덮어쓰지 마세요. **호스팅 운영 DB에 테스트를 실행하지 마세요.**

```bash
# 합성 로컬 DB에 Phase 2B가 아직 적용되지 않은 경우에만 한 번
npm run db:phase2b:local

npm run lint
npm run typecheck
npm test
npm run test:rls
npm run test:ai:db
npm run build
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:operations
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

운영 브라우저 테스트는 3001, 데모 테스트는 3004 포트를 사용합니다. 두 브라우저 테스트는 결과 디렉터리를 공유하므로 순서대로 실행하세요.

실제 유료 검증은 키·모델·검증된 가격 정책을 설정한 합성 로컬 환경에서만 다음 명령으로 실행합니다.

```bash
npm run test:ai:live
```

모델 조회 후 분석 1회와 5개 언어 번역을 실행하며 동일한 DB 비용·요청 제한을 적용합니다. 키가 없으면 종료 코드 2와 “미실행” 안내가 정상입니다. 모의 테스트 직후 같은 계정에 시간당 한도가 걸리면 시간이 지난 뒤 검증하세요. 실제 원고를 fixture로 사용하지 마세요.

## 남은 운영 검증

실제 모델·구조화된 출력 호환성, 5개 언어 번역 품질, 실제 과금, 호스팅 Supabase/Vercel 배포는 미검증입니다. 문자열 근거·구절 유효성·용어 검사는 의미 정확성과 신학적 타당성을 보장하지 못합니다. 성경 파서는 기본 절 구분과 정경 설정에 기반하므로 교단별 성경 차이를 검토해야 합니다. 목회자와 해당 언어 검수자가 최종 판단합니다.

작업에는 원문·결과 스냅샷이 보관됩니다. 교회별 RLS를 적용했지만 운영 보존·삭제 기간과 백업 정책은 정해야 합니다. service role 키는 RLS를 우회할 수 있으므로 서버 비밀 관리가 필수입니다. 이미지·음성·QR·자동 슬라이드 전환은 구현 범위가 아닙니다.
