# Phase 2B 실사용 검증 준비

현재 단계는 **준비 완료 / 실제 호출 미실행**입니다. 아래 절차는 사용자 또는 승인된 운영 담당자가 실행합니다. 이번 작업에서 호스팅 DB를 변경하거나 유료 API를 호출하지 않았습니다.

## 1. 호스팅 Supabase 적용 순서

운영과 분리한 검증 프로젝트를 우선 사용하세요. 운영 DB 변경은 별도 사용자 승인 이후에만 진행합니다.

| 순서 | 작업 | 확인 사항 |
| --- | --- | --- |
| 1 | 프로젝트 식별·백업·현재 스키마 확인 | 이미 적용한 SQL을 다시 실행하지 않음. 모르는 기존 테이블이 있으면 중단하고 검토 |
| 2 | `supabase/migrations/202610190001_phase2a.sql` 전체 적용 | churches, profiles, church_memberships, sermons, sermon_sections, translations, reviews 및 RLS |
| 3 | `supabase/migrations/202610190002_phase2b.sql` 전체 적용 | 버전 필드, sermon_analyses, sermon_translations, generation_jobs, ai_policy 및 RLS |
| 4 | Auth에서 최초 관리자 계정 생성 | 이메일/비밀번호 인증, 일반 가입 제한, 이메일 확인, Site URL·리다이렉트·SMTP 설정 |
| 5 | `supabase/bootstrap-admin.sql` 사본에서 사용자 UUID·교회명 지정 후 한 번 실행 | 기존 교회가 있다면 재실행하지 않음. 수정한 실제 값은 Git에 올리지 않음 |
| 6 | 서버 환경변수 설정·재배포 | 아래 목록 확인. 브라우저에 서버 키 노출 금지 |
| 7 | 로그인 후 /members에서 검수 담당자 권한 지정 | admin/pastor 최종 승인, media 편집·검수 요청 |
| 8 | 모델·공식 단가·상한 확인 후 ai_policy 활성화 | 초기 enabled=false 유지하다 검증 직전에 활성화 |

이 SQL은 재실행용 초기화 스크립트가 아닙니다. 이미 Phase 2A가 있다면 2번을 생략하고, Phase 2B도 있다면 적용하지 않고 확인만 합니다. SQL Editor로 적용한 경우 적용 기록을 별도로 남기세요. 파일은 트랜잭션 단위로 실행하고 실패하면 원인부터 확인합니다. 로컬 fixture/seed/test 스크립트를 호스팅 DB에 실행하지 않습니다.

## 2. 사용자가 설정할 항목

| 항목 | 설정 위치·주의 |
| --- | --- |
| APP_MODE=auto | 앱 서버 |
| NEXT_PUBLIC_SUPABASE_URL | 해당 호스팅 프로젝트 URL |
| NEXT_PUBLIC_SUPABASE_ANON_KEY | 공개 anon/publishable 키 |
| SUPABASE_SERVICE_ROLE_KEY | 서버 비밀 환경변수에만 저장 |
| OPENAI_API_KEY | 사용자가 발급한 실제 키를 서버 비밀 환경변수에만 저장 |
| OPENAI_MODEL | 계정에서 사용할 수 있고 구조화된 출력을 지원하는 모델. DB 정책과 일치 |
| ai_policy | 공식 가격으로 입출력 단가 수정, 건별·교회별·전체 비용 상한 및 요청 제한 확인 |
| 네트워크 | api.openai.com 및 정확한 Supabase 프로젝트 호스트 허용 |
| 배포 시간제한 | 서버 작업 최대 180초 지원 여부 확인 |

정책의 입력 1 / 출력 5 USD(백만 토큰당)는 미검증 예시입니다. 공식 요금 확인 전 활성화하지 마세요. OpenAI 프로젝트 지출 제한도 설정하세요. 키·비밀번호·원고·DB 접속 문자열을 채팅이나 저장소에 기록하지 않습니다.

현재 클라우드에는 OpenAI 키가 설정되지 않았습니다. 클라우드 프록시 비밀 등록의 OPENAI_ 접두사는 예약되어 있으므로 실제 앱 서버의 안전한 환경변수 설정 방식을 사용하세요. 자세한 설명은 [Phase 2B 설정](../phase-2b-setup.md)에 있습니다.

## 3. 공개 시험 원고

[sample-ko.txt](sample-ko.txt)는 이 프로젝트의 시험을 위해 새로 작성한 AI 교육용 요약이며 실제 목회자의 원고가 아닙니다. 개인 정보·개인 원고·특정 성경 번역본의 직접 인용을 포함하지 않습니다. 이 시험문은 공개 저장소에서 공유하고 서비스 검증에 복사·수정·번역하여 사용할 수 있도록 제공됩니다. 이는 다른 프로젝트 파일의 라이선스를 변경하지 않습니다.

제목: 하나님의 승리에 참여하려면? / 본문: 사사기 4:14-21.
실제 예배 설교로 표시하지 마세요. 2026년 10월 18일 설교의 전체 원고나 복원본이 아닙니다.

## 4. 실제 호출 절차

1. 검증 프로젝트에서 로그인 후 새 원고에 시험문 전체를 붙여넣거나 TXT로 올립니다. 제목에 “실사용 검증용 요약”을 표시합니다.
2. 분석 1회를 실행합니다. 장면 3~5개, 각 인용문과 문단 번호, 두 대지, 네 인물을 확인합니다.
3. ko, en, vi, ja, zh-CN을 각각 생성합니다. 각 언어의 작업 ID, 모델, 상태, 토큰, 비용을 비공개 검수 기록에 남깁니다.
4. [검수표](review-checklist.md)를 언어 담당자·목회자가 작성합니다. 저장 후 새로고침·재로그인해 결과가 유지되는지 확인합니다.
5. media의 최종 승인 차단과 pastor/admin 승인을 확인합니다. 승인 후 번역을 수정하면 승인이 해제되는지 확인합니다.
6. 다른 교회 계정에서 접근할 수 없는지 확인합니다. 익명 공개 URL은 이번 단계에서 계속 차단되어야 합니다.
7. 오류가 나면 안전한 실패 코드만 기록하고 원고가 유지되는지 확인합니다. 무작정 반복 호출하지 말고 예산과 원인을 확인한 뒤 재시도합니다.

분석 1회 + 5언어 생성은 총 6회이며 기본 사용자 제한 6회/시간을 모두 사용합니다. 추가 재생성은 한도 갱신 후 실행합니다. 실제 원고나 키가 담긴 화면 캡처·응답 로그를 Git에 추가하지 마세요.

기존 `npm run test:ai:live`는 별도의 짧은 합성 fixture를 사용하는 **로컬 전용** 검증 도구입니다. 위 공개 시험문을 검증할 때는 UI 절차를 사용합니다. 이번에 도구나 앱 기능은 변경하지 않았습니다.

## 5. 완료 조건

5개 언어가 모두 저장되고 검수표를 통과해야 합니다. 구조·문자열 검증만으로 의미·신학·번역 품질이 확인되지는 않습니다. 목회자 및 해당 언어 검수자의 확인 전 실제 예배에 사용하지 않습니다. 실제 테스트 결과는 아직 없으며 빈 검수표를 통과로 취급하지 않습니다.
